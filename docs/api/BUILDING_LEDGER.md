# 건축물대장 조회·비교

등록한 매물 상세의 **등록 주소로 검색 → 건축물대장 조회 → 건물 선택 → 호실 조회 → 이 호실로 비교 결과 저장**으로 사용합니다. 주소 검색은 Kakao 우편번호 서비스로 등록 주소를 검색하며 별도 키가 필요 없습니다. 선택한 법정동코드와 지번을 서버가 건축HUB API에 전달합니다. 등록 정보는 자동으로 덮어쓰지 않습니다.

## 설정

### 팀원이 처음 받아서 실행하기

Node.js 22.12 이상, Python 3, 실행 중인 Docker Desktop이 필요합니다. Windows에서는 WSL의 Bash에서 아래 명령을 실행하세요.

```bash
git clone --branch feat/building-ledger-comparison https://github.com/jisunghaha/RoomCrossCheck.git
cd RoomCrossCheck
npm ci
cp .env.example .env
```

로컬 `.env`의 `BUILDING_REGISTER_API_KEY`에 본인 인증키 또는 별도로 전달받은 키를 입력하세요. Gemini도 사용하려면 `GEMINI_API_KEY`를 입력하고 `GEMINI_ENABLED=true`로 바꿉니다. 건축물대장 기능만 사용할 때는 Gemini 설정이 필요 없습니다. 실제 키가 담긴 `.env`는 저장소에 포함되지 않습니다.

```bash
./scripts/dev-up.sh
VITE_DATA_MODE=listing-api VITE_API_BASE_URL=/api npm run dev
```

DB 비밀번호가 비어 있으면 실행 스크립트가 로컬 값을 생성합니다. 터미널에 표시된 프론트 주소로 접속하고 매물을 등록한 뒤 상세 화면에서 조회하세요. 기본 프론트 포트는 4173이며 사용 중이면 다음 포트로 실행됩니다. 백엔드 기본 포트 8080이 사용 중이면 아래와 같이 맞춥니다.

```bash
ROOM_BACKEND_PORT=8081 ./scripts/dev-up.sh
VITE_DATA_MODE=listing-api VITE_API_BASE_URL=/api DEV_API_TARGET=http://127.0.0.1:8081 npm run dev
```

이 저장소의 예시 이미지는 가상 주소를 사용하므로 건축물대장 실제 조회에는 아래의 실제 주소 예시 또는 조회 가능한 매물 주소를 사용해야 합니다. 기존 개발자의 DB·브라우저 저장 자료는 Git에 포함되지 않습니다.

로컬 `.env`에 `BUILDING_REGISTER_API_KEY`를 설정하고 백엔드를 재시작합니다. Docker Compose가 서버에만 전달합니다. 프론트엔드는 `VITE_DATA_MODE=listing-api`, `VITE_API_BASE_URL=/api`로 실행합니다. 인증키는 `VITE_` 설정이나 Git에 넣지 않습니다.

공식 자료: [건축HUB 건축물대장정보 서비스](https://www.data.go.kr/data/15134735/openapi.do), [Kakao 우편번호 가이드](https://postcode.map.kakao.com/guide).

## 서버 계약

`POST /api/listings/{id}/official/search`

```json
{"legalCode":"1168010600","bun":"316","ji":"0","landType":"0"}
```

`legalCode`는 10자리 법정동코드입니다. `landType`은 일반 0, 산 1이며 지번 본번·부번은 최대 4자리입니다. 응답은 `searchId`, `buildings`, `units`, `message`입니다. 건물을 선택하고 같은 요청에 `buildingId`, `ho`를 추가하면 해당 동·호의 전유면적을 조회합니다.

`PUT /api/listings/{id}/official`

```json
{"searchId":"조회 응답의 ID","buildingId":"조회한 건물 ID","unitId":"조회한 호실 ID"}
```

`unitId`가 null이면 건물 정보만 저장합니다. 공식 값 자체를 클라이언트에서 받지 않으며 서버가 보관한 실제 조회 결과로만 저장합니다. 조회 결과는 10분 뒤 만료되고, 매물이 수정되면 이전 조회 결과로 저장할 수 없습니다. 프로세스 재시작 시 미저장 조회는 만료됩니다. 저장한 공식 기록은 `listings.official` JSON 필드에 남습니다. 로컬 스키마는 기존 `ddl-auto=update` 설정을 따르며 팀 Flyway DB에는 별도 마이그레이션이 필요합니다.

## 비교 규칙

- 주소: 공식 도로명·지번주소와 등록 주소를 비교합니다. 일부 지역 약칭, 공백, 괄호 참고주소, 번지 표기를 정규화합니다. 뒤에 붙은 숫자 동·층·호는 기본주소 비교에서 허용하지만 해당 상세주소까지 검증했다는 뜻은 아닙니다. 다른 표기·건물명만 입력한 주소는 차이로 표시될 수 있으므로 사용자가 확인해야 합니다.
- 면적: 선택한 동일 동·호실의 `전유` 자료만 합산하고 등록 면적 종류가 `전용`일 때 비교합니다. 허용오차는 기존 규칙인 0.5㎡입니다. 공용면적·건물 연면적·층 전체 면적은 대신 사용하지 않습니다.
- 동·호실: 등록 주소에 숫자·영문 동·호실이 있으면 선택한 공식 호실과 따로 비교합니다. 주소에 호실이 없으면 동일 호실 여부는 비교 불가입니다.
- 층수: 동일 호실 전유 자료에 지상·지하 구분과 층수가 있어야 비교합니다. 지하는 음수이며 여러 층에 걸친 호실은 비교 불가입니다.
- 공식 면적 누락·0, 호실 미조회, 공급/미상 면적은 면적 비교 불가입니다. 층수·면적 비교 불가는 일치율 분모에서 제외합니다.
- 보증금·월세·관리비는 건축물대장으로 검증하지 않습니다. 용도·사용승인일·건물 전체 층수는 참고 정보입니다.
- 매물을 수정하면 공식 기록을 해제하여 재조회하게 합니다. 주소가 다를 경우 공식 대상이 맞는지 사용자가 다시 확인해야 합니다. 전체 항목 일치가 매물의 안전성이나 모든 광고 내용의 진위를 보장하지 않습니다.

## 오류와 확인

인증 설정 누락, 인증/이용 한도 오류, 연결 실패, 자료 없음은 각각 안내합니다. 조회 실패 시 기존에 저장한 공식 기록은 보존합니다. 페이지가 여러 개면 전체 결과를 읽으며, 30,000건 초과 또는 누락 응답은 부분 결과로 저장하지 않습니다.

HTTP 408·500·502·503·504, 연결 시간 초과, HTTP 200의 비정상 응답은 각 페이지에서 최대 3회 요청합니다. 요청 간 짧은 대기 시간을 두며 인증·이용 한도 오류는 자동 재시도하지 않습니다. 공식 서버 장애가 지속되면 재시도 후에도 실패할 수 있습니다.

완전한 성공 결과는 지번·작업 종류·동·호실별로 서버 메모리에 10분간 캐시합니다. 자료 없음 응답은 1분만 보관하며 오류·부분 결과는 저장하지 않습니다. 서버를 재시작하면 캐시는 초기화됩니다. 화면에는 캐시 재사용 여부와 원래 공식 조회 시각을 표시합니다. 건물과 호실의 조회 시각이 다르면 저장 기록에는 더 이른 시각을 사용합니다. 만료된 캐시를 최신 조회 결과처럼 대신 반환하지 않습니다.

수동 조회 예시: 법정동코드 `1168010100`, 본번 `737`, 부번 `0` → 강남파이낸스센터. 이 건물은 호실별 전유 자료가 없어 건물 정보만 확인하는 예시입니다. 집합건물 호실 예시: `1168010600`, `316`, `0`, 은마아파트 26동 808호. 실제 자료 변경·가용성에 따라 응답은 달라질 수 있습니다.

현재 로컬 개발 서버는 기존 브랜치와 같이 로그인·소유권 검증을 제공하지 않습니다. 운영 연결 전에 사용자별 조회·저장 권한을 추가해야 합니다.

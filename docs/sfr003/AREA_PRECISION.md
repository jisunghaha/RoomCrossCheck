# 면적 정밀도 보완

2026-11-03, 기준 커밋 02a8d47. 실제 부산 이미지 검증에서 발견한 19.212㎡·14.876㎡의 폼 입력 차단과 DB 반올림 문제를 보완했다. 과거 실제 Gemini 결과는 변경하지 않고 저장된 응답을 로컬에서 재생했다. 이번 외부 Gemini 요청은 0건이다.

## 저장 계약

- 최종 매물 면적은 0~100000㎡ 또는 null이며, 유효 소수는 최대 4자리다. 팀 rooms의 DECIMAL(10,4) 방향과 동일하게 개발용 listings.area도 DECIMAL(10,4)로 맞췄다. 팀 rooms·Flyway V1은 변경하지 않았다.
- 폼 step은 0.0001이다. 19.212·14.876·23.7501을 그대로 저장한다. 범위 또는 유효 소수 4자리를 초과하면 최종 API가 400으로 거부하며 몰래 반올림하지 않는다. 의미 없는 끝자리 0은 값 손실 없이 정리한다.
- Gemini 추출 JSON과 사용자 확인 JSON은 원값을 별도로 보존한다. 더 세밀한 값은 최종 폼에서 사용자가 확인·수정해야 한다. null과 0은 구분한다.
- 현재 시연 비교의 0.5㎡ 허용오차는 바꾸지 않았다. 15.876과 16.376의 차이가 JavaScript에서 0.5000000000000018로 계산되는 경계 오차만 기계 정밀도 범위에서 보정했다. 15.8761과 16.3762처럼 실제로 경계를 넘는 값은 일치로 처리하지 않으며 표시용 반올림을 판정에 사용하지 않는다. 실제 공식 조회·7개 항목 API의 완성을 뜻하지 않는다.

## 기존 DB 보호

DECIMAL(10,2)의 정수부는 8자리지만 DECIMAL(10,4)는 6자리다. 999999.9999 범위를 넘는 기존 값이 있으면 변환할 수 없으므로 임의 절삭하거나 삭제하지 않는다. API의 업무 상한 100000㎡와 DB의 표현 가능 상한은 구분한다.

개발용 SQL·사전 조회·백업·복구 기준은 sql/README.md와 upgrade_listing_area_precision.sql을 따른다. SQL은 세션의 기존 sql_mode를 보존하며 STRICT_ALL_TABLES를 추가한다. 앱의 MySQL 연결도 같은 방식으로 엄격 모드를 보장하고, Hibernate 스키마 오류가 나면 시작을 중단한다. 로컬 ddl-auto=update가 스키마를 변경할 수 있으므로 기존 데이터가 있는 DB에서는 앱 실행보다 먼저 백업·사전 검사·명시적 이행을 수행해야 한다.

이미 이전 버전에서 19.212가 19.21로 저장됐다면 컬럼을 넓혀도 원래 자릿수가 복원되지는 않는다. 광고 원본·추출 JSON·확인 JSON과 대조한 별도 복구가 필요하며 이번에 자동으로 역추정하거나 덮어쓰지 않았다. 코드 롤백 때문에 10,2로 다시 줄이면 새로운 소수 값이 손실될 수 있으므로 자동 축소하지 않는다.

- 서버 재시작 후 매물·추출·확인 응답이 모두 유지됐다. 원본 이미지와 이전 실제 Gemini 호출 기록은 변경하지 않았다.
